# First Simulations

> Note: this guide serves as the basis for this module - they go into a lot more detail about what some of the commands mean [Introduction to ROS2: Sending and Receiving your First ROS2 Messages](https://classes.cs.uchicago.edu/archive/2025/fall/20600-1/ros2_intro.html)
{: .prompt-tip }

Our goal for this module is to get some basic simulations up and running, including defining the environment, instantiating robots, and deploying a basic controller to have that robot navigate from one waypoint to another.  We will do both the iRobot Create3 and bitcraze Crazyflie 2.1.  

> The general premise for these guides now will be to first **recreate** the tutorial, **extend** the tutorial (answers available), and then complete the **homework** for the tutorial (answers not available).

We have two goals for this guide for each robot.  First, we want to recreate the talker/listener from the ROS setup guide, however in the context of our robots:

> We want them to tell us their `[x, y, z]` position.

Second, each of our robots must navigate to a set of waypoints and indicate success or failure at the end of the time limit.  This will involve (1) setting a waypoint in space for both and (2) developing and executing a basic controller for each robot.

For now we aren't going to worry about the environment at all or any form of obstacle avoidance, we simply want to trigger the motors to move and have them tell us about it.

> I am not covering the entirety of ROS or its infrastructure and that will become quite obvious in this section.  We are going to get simulations up and running and you'll pick it up as you go.  **Please refer to existing ROS textbooks/guides for a detailed overview of ROS**. 
{: .prompt-warning }

Inside the `create3_demo_talker_py/create3_demo_talker_py` directory, create a new file called `undock_and_talk.py`.  Let's add some code to have the robot first undock (meaning, disengage from its charging station and back up) and then turn around.

The following code will import the basics of what we need.  Check the comments for what is going on.

```python
# Code based on: https://github.com/tuftsceeo/Tufts_Create3_Examples/blob/main/Code/Package/example_package/action_undock.py
TODO USE THE ABOVE CODE INSTEAD AND TWEAK

import rclpy
from rclpy.node import Node
from rclpy.action import ActionClient
from geometry_msgs.msg import Twist
from irobot_create_msgs.action import Undock

class Create3DemoNode(Node):
    def __init__(self):
        super().__init__('create3_demo_node')
        
        # 1. Action Client for Undocking
        self._undock_client = ActionClient(self, Undock, 'undock')
        
        # 2. Publisher for direct velocity control (/cmd_vel)
        self._cmd_vel_pub = self.create_publisher(Twist, 'cmd_vel', 10)
        
        self.get_logger().info('Create 3 Demo Node initialized. Undocking...')
        self.send_undock_goal()

    def send_undock_goal(self):
        if not self._undock_client.wait_for_server(timeout_sec=5.0):
            self.get_logger().error('Undock action server not available!')
            return

        goal_msg = Undock.Goal()
        future = self._undock_client.send_goal_async(goal_msg)
        future.add_done_callback(self.undock_response_callback)

    def undock_response_callback(self, future):
        goal_handle = future.result()
        if not goal_handle.accepted:
            self.get_logger().info('Undock goal rejected.')
            return

        self.get_logger().info('Undock goal accepted! Executing...')
        result_future = goal_handle.get_result_async()
        result_future.add_done_callback(self.undock_finished_callback)

    def undock_finished_callback(self, future):
        self.get_logger().info('Undock complete! Rotating in place...')
        self.spin_robot()

    def spin_robot(self):
        msg = Twist()
        msg.angular.z = 0.5 # radians/sec
        
        # Publish velocity command for 3 seconds
        for _ in range(30):
            self._cmd_vel_pub.publish(msg)
            rclpy.spin_once(self, timeout_sec=0.1)

        # Stop
        msg.angular.z = 0.0
        self._cmd_vel_pub.publish(msg)
        self.get_logger().info('Demo execution finished!')

def main(args=None):
    rclpy.init(args=args)
    node = Create3DemoNode()
    rclpy.spin(node)
    node.destroy_node()
    rclpy.shutdown()

if __name__ == '__main__':
    main()
```

The code above, by itself, will have the robot move around in your simulator.  We now need to wire everything else up and then we can test.

## Add Talker

Now let's extend our code to communicate our position information.  


What we're going to do is **create a custom topic** that we will send information to.  Let's call it `/robot_current_pose`.  Within your `undock_and_talk.py` file:

```python
from geometry_msgs.msg import Twist, PoseStamped # <-- changed

class Create3DemoNode(Node):
    def __init__(self):
        super().__init__('create3_demo_node')
        
        self._undock_client = ActionClient(self, Undock, 'undock')
        
        self._cmd_vel_pub = self.create_publisher(Twist, 'cmd_vel', 10)

        # NEW CODE
        # create our 'talker' publisher that sends out our position periodically
        self._talker_pub = self.create_publisher(PoseStamped, '/my_pose', 10) 
        # create a callback timer so our message gets published periodically
        self.talker_timer = self.create_timer(0.5, self.timer_callback)  # send every 2 Hz
        
        self.get_logger().info('Create 3 Demo Node initialized. Undocking...')
        self.send_undock_goal()

    # ALSO NEW CODE
    # callback function to publish position information periodically
    def timer_callback(self):
        msg = PoseStamped()
        msg.header.stamp = self.get_clock().now().to_msg()
        msg.header.frame_id = "odom"
        msg.point.x = 1.0
        msg.point.y = 2.0
        msg.point.z = 0.0
        self._talker_pub.publish(msg)
        self.get_logger().info(f'Publishing: [{msg.point.x}, {msg.point.y}, {msg.point.z}]')
```

Rebuild everything (see above) and run.  You *should* see your logging messages printing to the terminal.

## Add Listener

The robot is talking, but who is listening?  Nobody, that's who!  We need another node to respond.  A pong for the ping, so to speak.  If you recall from the setup test, we launched two separate nodes - the talker and the listener.  What we have done *here* is to launch the simulator and launch the talker - we need to launch the listener as well!


Create a new file (`receiver.py`) in the same source directory (i.e., `src/create3_demo_talker_py/create3_demo_talker_py/receiver.py`).

In that file, we're going to create another class (with its own `spin` mechanism) that will be operating *independently* of your other script.  It will launch in its own terminal as well.

Add the following code:

```python
import rclpy
from rclpy.node import Node
from geometry_msgs.msg import PoseStamped

class PoseLocationReceiver(Node):
    def __init__(self):
        super().__init__('receive_pose_location')
        self.subscription = self.create_subscription(
            PoseStamped,
            '/robot_current_pose',
            self.listener_callback,
            10)

    def listener_callback(self, msg):
        self.get_logger().info(f'Received: [{msg.pose.position.x:.2f}, {msg.pose.position.y:.2f}, {msg.pose.position.z:.2f}, {msg.pose.orientation.x:.2f}, {msg.pose.orientation.y:.2f}, {msg.pose.orientation.z:.2f}, {msg.pose.orientation.w:.2f}]')

def main(args=None):
    rclpy.init(args=args)
    node = PoseLocationReceiver()
    rclpy.spin(node)
    node.destroy_node()
    rclpy.shutdown()

if __name__ == '__main__':
    main()
```

Looks similar to the other script, except here our class is solely tasked with listening to the `/robot_current_pose` topic and printing out its data structure.  

> Note: you can figure out what the attributes are by monitoring the ros topic in the terminal.  See the end of the prior section.
{: .prompt-tip }

You also will need to register the script within your `setup.py` file:

    entry_points={

            'undock_and_talk = create3_demo_talker_py.undock_and_talk:main', 
            'receiver = create3_demo_talker_py.receiver:main', # <-- add this line
        ],
    },

And then rebuild and re`source` your project in **each** of your terminal windows.

## Command via ROS topics

Last but not least, we can send the same commands via the terminal.  The use case for this is if you want to manually control it from some other point (or you want to do something like trigger a button and have it send a command - not necessarily constrained to `rclpy`).

In terminal 1, launch your simulation as usual:

```bash
ros2 launch irobot_create_gz_bringup create3_gz.launch.py
```

In terminal 2, send a command to reverse:

```bash
ros2 topic pub -r 20 /cmd_vel geometry_msgs/msg/TwistStamped "{header: {stamp: {sec: 0, nanosec: 0}, frame_id: 'base_link'}, twist: {linear: {x: -0.2, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 0.0}}}"
```

As a reminder, **once the simulation is running**, you can run `ros2 topic list` to get a list of all the available ROS topics that you can play with.  

Above, we're publishing to the `/cmd_vel` topic with a `TwistStamped` message.  We need the stamp, at least in Jazzy (for the Humble guide normal `Twist` messages work -- I couldn't get them to work in Jazzy), for the robot to accept the command.  If you dig into the message we're sending a linear and angular velocity.

The opposite direction now would be: 

```bash
ros2 topic pub -r 20 /cmd_vel geometry_msgs/msg/TwistStamped "{header: {stamp: {sec: 0, nanosec: 0}, frame_id: 'base_link'}, twist: {linear: {x: 0.1, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 0.0}}}"
```
